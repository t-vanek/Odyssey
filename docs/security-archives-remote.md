# Archive and remote-operation security model

## Archives

Supported archives are exposed as panel locations. ZIP browsing, extraction and writing use managed .NET APIs. ZIP explicitly advertises create, update and entry-delete capabilities; 7z, TAR, TAR.GZ, GZip, BZip2, XZ and RAR remain browse/extract-only and are advertised only when Odyssey has initialized its native 7-Zip engine. Unsupported write operations are rejected at the queue boundary.

Every entry name is canonicalized before it is shown or extracted. Empty segments, `.`/`..`, absolute and drive-qualified paths, NULs, excessive depth, platform-invalid names, and duplicate or case-colliding paths reject the archive. Entries advertised as symbolic links/reparse points are visible for inspection but cannot be extracted; extracting a tree containing one also fails. The archive source and every existing destination ancestor must be a real file/directory rather than a link boundary.

Scanning enforces configurable entry-count, depth, single-entry, total-expanded-byte and (where compressed sizes are available) compression-ratio limits. The default ceilings are 50,000 entries, depth 64, 4 GiB per entry, 20 GiB total expanded data and ratio 1,000:1. These are safety ceilings, not promises that enough destination space exists. Extraction performs a free-space preflight, streams through a length- and cancellation-guarded writer, and never buffers a complete large entry in memory.

Extracted output is first written beneath a randomly named staging directory inside the destination filesystem, then published with a same-filesystem move. Conflict policy is applied only after successful extraction. Replace temporarily moves the previous destination aside and restores it on a reported publication error. Cancellation or a handled failure removes staging data. Extraction staging is not yet journaled across a process or power loss; an internal staging artifact can therefore remain for manual cleanup. The source archive is never changed by extraction.

Every ZIP mutation enumerates and validates the original plus all local inputs before publication. Local inputs and every ancestor are rejected if they are links/reparse points; length and modification time are rechecked around streaming. Retained entries and additions are streamed into a transaction-ID-named sibling ZIP using the store method, the complete result is rescanned through the hostile-archive policy, and the old archive is replaced only after validation. Before the first publish move, Odyssey durably records the exact destination, temporary path, optional backup path and transaction state beneath application data. A caught publication failure restores the original byte-for-byte backup. On restart, recovery runs before the transfer worker and either completes an already validated move or restores the validated backup; only exact sibling artifacts derived from the manifest ID can be touched. Oversized, malformed, path-mismatched, linked or corrupt recovery artifacts are left in place and reported instead of being applied automatically. No file contents or credentials are stored in the journal.

Archive→archive copying is not server-side. The durable queue extracts the selected source tree into a random, link-validated relay directory beneath Odyssey application data, performs the same complete target rewrite, and removes the relay in `finally`. On startup, only stale `relay-<GUID>` directories below that exact controlled root are removed, using a traversal that deletes links themselves and never follows them. Unrelated names are preserved. Relay paths contain no credentials.

Encrypted entries are rejected until a separate non-persisting password workflow exists. Quick View of an unextracted entry, non-ZIP creation/mutation, archive-mutation Undo, hardlink-format interpretation beyond attributes exposed by the reader, and crash reconciliation for extraction staging are not implemented yet.

## Remote operations

Remote secrets are deliberately separated from durable jobs. Queue records may contain endpoint type, paths, policies and opaque session keys, but never passwords, tokens, private keys or key contents. Server identity validation is mandatory: SFTP requires an exact host-key fingerprint, and future TLS providers must validate certificate identity without a global bypass.

Remote copies use bounded streaming rather than whole-file buffering. A temporary destination is not presented as complete. Links are not automatically followed across the trust boundary. Read-only mode blocks remote mutations just as it blocks local mutations. Current SFTP does not yet implement byte-range resume, reconnect/backoff, credential vaults, or remote→remote relay; see [remote connections](remote-connections.md) and [the roadmap](commander-roadmap.md).
